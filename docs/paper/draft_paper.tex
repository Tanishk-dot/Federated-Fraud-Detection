\begin{abstract}
Fraud detection across financial institutions is fundamentally a
multi-party problem: fraud patterns are strongest when observed across
many institutions' data, yet that data cannot be legally or
competitively pooled. This paper presents a fraud detection system built
around a Temporal Graph Transformer with a contrastive learning head,
trained via federated learning across ten simulated bank clients, with
every round's aggregate protected by client-level differential privacy,
homomorphic encryption, and an optional secure-aggregation topology, all
three exercised in training rather than left as reference code. Results
are measured rather than asserted: a four-model baseline comparison and
a full privacy-utility sweep, each run on a synthetic dataset and on 1.9
million real PaySim transactions. The real-data evaluation required
fixing a genuine upstream defect first: every client's delivered
validation and test split was entirely fraudulent, traced and rebuilt
before trusting any number. A batch-level fraud-starvation failure mode
required a further fix, weighted oversampling, before most models could
learn beyond a constant prediction, a structural finding about this
architecture's regularization needs under severe imbalance rather than
a tuning footnote. Formal multi-round differential-privacy composition
accounting further corrected every privacy-budget value reported in
prior work: the classical noise-calibration approach used is tight only
in a narrow regime, and at the project's chosen operating point the
true cost is several times larger than the nominal label. Every result
is reported in full, including findings that look worse than a rounder
number would, since a privacy-utility claim is only as credible as the
pipeline and accounting behind it.
\keywords{federated learning, differential privacy, fraud detection, temporal graph transformer, homomorphic encryption}
\end{abstract}

\section{Introduction}

Financial fraud detection sits at an awkward intersection of two facts.
First, fraud is inherently a cross-institution phenomenon: a fraud ring
that touches five banks looks like five separate, individually
low-signal anomalies to each bank in isolation, and only becomes visible
as a pattern when the five views are combined. Second, banks cannot
combine those views. Data protection regulation, competitive concerns,
and the sheer sensitivity of transaction-level financial data make
centralizing raw records across institutions a non-starter in practice,
regardless of its modeling appeal.

Federated learning (FL)~\cite{mcmahan2017fedavg} offers a way out of
this bind: institutions train a shared model collaboratively while each
institution's raw data never leaves its own infrastructure, only model
updates are exchanged. But federated learning by itself is not a privacy
guarantee -- a client's model update can still leak information about
its training data~\cite{mcmahan2018dp,abadi2016dpsgd}. Differential
privacy (DP)~\cite{dwork2014dp}, applied at the client-update level,
closes that gap by bounding and noising each round's aggregate update,
at a cost: DP noise degrades model utility, and the size of that cost is
an empirical question, not something that can be waved away. Homomorphic
encryption~\cite{paillier1999} and secure aggregation~\cite{bonawitz2017secagg}
add a complementary, cryptographic guarantee on top of DP's statistical
one: the server never observes an individual client's update in
plaintext at all, not just a noised version of it.

This paper makes four contributions, each grounded in a real, measured
run rather than an assumption. First, we describe a fraud detection
architecture -- a Temporal Graph Transformer with a contrastive learning
head -- trained under FedProx~\cite{li2020fedprox} with client-level
DP-FedAvg~\cite{mcmahan2018dp}, and report its performance against real,
non-fabricated baselines on one shared held-out test set
(Section~\ref{sec:results}). Second, we repeat every such measurement on
1.9 million real PaySim transactions~\cite{lopezrojas2016paysim}, not
only a synthetic stand-in, after finding and fixing a genuine
data-quality defect in the delivered splits
(Section~\ref{sec:realdata}). Third, we wire Paillier homomorphic
encryption and a tiered secure-aggregation topology into the live
training loop -- previously correct but disconnected reference code --
and report their real, measured computational overhead
(Section~\ref{sec:he}). Fourth, we implement formal multi-round
R\'enyi-DP composition accounting and report the real cumulative privacy
cost of a training run, which turns out to correct, not merely
supplement, every per-round $\varepsilon$ value this project has
previously reported (Section~\ref{sec:accounting}). We consider the
discipline behind these four contributions -- measuring rather than
asserting, and reporting defects and corrections rather than only
successes -- as important as the headline numbers themselves.

\section{Related Work}

\textbf{Federated learning.} McMahan et al.~\cite{mcmahan2017fedavg}
introduced FedAvg, the foundational algorithm for training a shared
model across decentralized clients by averaging locally-trained weights.
FedAvg assumes client data is approximately independent and identically
distributed (IID); in a cross-bank setting this assumption does not
hold, since each bank's transaction mix, fraud rate, and customer
behavior differ systematically. Li et al.~\cite{li2020fedprox} address
this with FedProx, which adds a proximal term to each client's local
objective that penalizes drift from the global model, stabilizing
training under non-IID data -- the algorithm we adopt for this reason.

\textbf{Differential privacy in federated learning.} Applying DP
naively -- clipping and noising gradients at every local minibatch --
both destroys utility and, without careful composition accounting,
provides a weaker guarantee than its stated $\varepsilon$ suggests.
McMahan et al.~\cite{mcmahan2018dp} instead propose DP-FedAvg: each
client clips its \emph{entire round update}, and the server adds a
single calibrated Gaussian noise draw to the aggregate, once per round.
This is the mechanism we use. Abadi et al.~\cite{abadi2016dpsgd}
established the moments-accountant approach to composing privacy loss
across many training steps; Mironov~\cite{mironov2017rdp} generalized
this into R\'enyi differential privacy (RDP), a composition framework
that is tight for the Gaussian mechanism specifically and the one we
adopt for multi-round accounting in Section~\ref{sec:accounting}. Dwork
and Roth~\cite{dwork2014dp} give the formal $(\varepsilon,\delta)$-DP
definition, and the classical Gaussian-mechanism calibration bound whose
valid regime we re-examine in Section~\ref{sec:accounting}.

\textbf{Secure aggregation and encryption.} Bonawitz et
al.~\cite{bonawitz2017secagg} describe secure aggregation protocols that
let a server compute a sum of client updates without seeing any
individual update, and Paillier's cryptosystem~\cite{paillier1999}
underlies additively homomorphic aggregation schemes with the same
goal. Both are complementary, cryptographic guarantees to DP's
statistical one; an earlier phase of this project implemented a
reference version of both without wiring them into the live training
loop. Section~\ref{sec:he} reports both now exercised in training, with
real measured overhead.

\textbf{Model architecture.} Our temporal branch is a standard
Transformer encoder~\cite{vaswani2017attention} applied over a fixed
window of a client's recent transactions. Our auxiliary contrastive
head follows the general contrastive representation-learning framework
of Chen et al.~\cite{chen2020simclr}, adapted here to encourage
separation between fraud and legitimate transaction embeddings rather
than between augmented views of the same image.

\textbf{Federated fraud detection systems in the literature.} A growing
body of work applies FL specifically to financial fraud and
financial-crime detection, under a range of architectures and privacy
mechanisms. Zhang et al.~\cite{zhang2023hyfl} address the case where
transaction-level and account-level features are held by different
institutions, combining horizontal and vertical FL into a hybrid
framework (HyFL) evaluated on a real $\approx$3M-transaction SWIFT
dataset at 1:783 imbalance; Suzumura et al.~\cite{suzumura2019fedgraph}
instead federate \emph{graph} features across institutions for
anti-money-laundering, reporting a $\approx$20\% accuracy improvement
over isolated local models on the UK FCA TechSprint dataset --
motivating evidence for exactly the kind of cross-institution graph
signal our own graph branch is intended for, though not yet wired to
real entity-linked edges (Section~\ref{sec:graphbranch}). Sun's
comparative study~\cite{sun2025fedsurvey} benchmarks ANN, Random
Forest, and CNN clients under FL specifically for fraud, finding RF
more robust to non-IID data but communication-heavier -- a tradeoff our
own choice of FedProx (Section~III-B) is one answer to without changing
the base architecture per client.

A second cluster addresses the transparency gap FL alone doesn't close.
Awosika et al.~\cite{awosika2024xaifl} and Aljunaid et
al.~\cite{aljunaid2025xfl} both pair FL with post-hoc explainability
(SHAP/LIME) so that a federated model's decisions remain auditable to
analysts despite no institution seeing another's raw data -- a concern
this paper does not address directly (our contrastive head targets
novel-pattern separation, not instance-level explanation) but flag as
complementary future work. Kanamori et al.~\cite{kanamori2022deepprotect}
report one of the few real-world FL deployments in this space:
DeepProtect, piloted across five live Japanese banks using additive
homomorphic encryption for gradient aggregation, detecting fraudulent
accounts weeks before manual bank processes did -- a real-world existence
proof for exactly the HE-secured aggregation path this paper wires into
training in Section~\ref{sec:he}, at smaller (simulated, ten-client)
scale. Zheng~\cite{zheng2025wgandp} tackles class imbalance directly
inside the privacy layer, combining adaptive differential privacy with
WGAN-based synthetic minority generation; our own imbalance fix
(Section~\ref{sec:realdata}) instead oversamples real examples rather
than generating synthetic ones, a simpler but real-data-only
alternative. Tang and Liu~\cite{tang2024sdt} and Abbassi et
al.~\cite{abbassi2025vaeqlstm} both federate sequence architectures
(a Transformer-based Structured Data Transformer, and a VAE-QLSTM
fusion respectively) for transaction-level fraud, supporting this
paper's own choice of a temporal Transformer branch (Section~III-A) as
a reasonable federated sequence model for this task. Finally, Han
Zheng~\cite{hzheng2025fedgat} compares FedGAT-DCNN, FedAvg+CNN, and a
data-quality-weighted FedAvg-DWA+RF, finding the graph-attention variant
strongest on imbalanced data -- further, independent support (beyond
Suzumura et al.) for graph-structured federated fraud models, which our
own graph branch approximates only partially today.

None of the above systems' reported metrics are reused as numeric
comparison points in Table~\ref{tab:comparison} or
Table~\ref{tab:comparison-real}: every number in those tables comes from
a model we trained ourselves under one controlled, single-test-set
protocol, since cross-paper metric comparisons across different
datasets, splits, and imbalance ratios are not a defensible apples-to-
apples claim regardless of how well each individual source is cited.

\section{System Architecture}

\subsection{Temporal Graph Transformer}
\label{sec:graphbranch}
Each client account's transaction history is windowed into a
fixed-length sequence of its ten most recent transactions, each encoded
as a 10-dimensional feature vector (normalized amount, hour-of-day,
day-of-week, a merchant-category risk score, distance from the
previous transaction, time since the previous transaction, an implied
velocity, card age, transaction frequency in the last 24 hours, and a
weekend flag). A four-layer Transformer encoder processes this
sequence. A parallel graph branch encodes each account's own transaction
profile; in the experiments reported here this branch operates on each
account as an isolated node, not a multi-entity relational graph. A
real heterogeneous graph encoder (HGTConv, 3 layers/8 heads) is fully
implemented but needs real entity-linked edges -- shared user/merchant/
card/device identifiers -- that the preprocessed sequence data does not
carry, so what runs in the experiments below is the simplified
per-account encoder instead. A cross-modal fusion
layer combines the two branches via bidirectional attention. Two heads
sit on top of the fused
representation: a supervised binary cross-entropy head for the primary
fraud/legitimate decision, and a contrastive head intended to separate
novel fraud patterns from the learned representation space even when
they were not explicitly labeled as such during training.

The model is deliberately small: a 32-dimensional hidden size, giving
approximately 45{,}000 parameters. Section~\ref{sec:lessons} explains
why this specific choice -- rather than a larger, seemingly more
capable model -- is load-bearing for both training stability and the
differential privacy mechanism's usable operating range.

\subsection{Federated Training: FedAvg and FedProx}
Training is simulated across ten clients, each representing one bank
with its own transaction distribution. Each round samples a subset of
clients, each of which trains locally for several epochs before sending
its update to the server. The server aggregates client updates with
FedProx's proximal-term regularization ($\mu=0.1$), which penalizes a
client's local update for drifting far from the current global model --
the mechanism that keeps training stable when only a minority of
clients are sampled per round and those clients disagree with each
other's local optima. The ten simulated clients here draw from
independent but not systematically heterogeneous distributions --
genuine per-institution non-IID structure, with different fraud
patterns rather than just different random samples, is not yet modeled,
even though it is part of why FedProx was chosen over plain FedAvg in
the first place. Section~\ref{sec:realdata} reports that this
regularization is not merely helpful but \emph{necessary} on real data
under severe class imbalance: the FedAvg-no-DP baseline, which lacks it,
fails to learn a usable decision boundary even with the same data fix
applied.

\subsection{Client-Level Differential Privacy}
\label{sec:dp-mechanism}
Each client's update is clipped to a fixed $L_2$ norm (clip norm
$=1.0$) before being sent to the server. Once per round, the server adds
a single Gaussian noise draw to the aggregated update, scaled by the
largest single client's averaging weight -- the aggregate's sensitivity
to any one client's contribution, rather than the full per-client clip
norm, following the client-level DP-FedAvg construction of McMahan et
al.~\cite{mcmahan2018dp}. This gives an $(\varepsilon,\delta)$-DP
guarantee at the level of ``one client's entire round contribution,''
which is the right unit of protection in a cross-silo setting where each
client is an institution, not an individual data subject.

Gaussian-mechanism noise scales with $\sigma\sqrt{d}$ for a
$d$-dimensional update, meaning the number of trainable parameters
directly determines how much noise a fixed $\varepsilon$ requires. This
is precisely why the model's size (Section~III-A) and its DP budget are
not independent design choices. The noise scale $\sigma$ itself is
calibrated from a target $\varepsilon$ via the classical Gaussian
mechanism bound $\sigma = \Delta\sqrt{2\ln(1.25/\delta)}/\varepsilon$
(Dwork and Roth~\cite{dwork2014dp}); Section~\ref{sec:accounting} shows
that this formula's proof is tight only for $\varepsilon \le 1$, with
direct consequences for every $\varepsilon$ value reported in this
paper.

\subsection{Homomorphic Encryption and Secure Aggregation}
\label{sec:he}
An earlier phase of this project implemented Paillier additive
homomorphic encryption~\cite{paillier1999} and a tiered proxy-server
secure-aggregation topology~\cite{bonawitz2017secagg} as correct
reference code, disconnected from the live training loop. Both are now
exercised in training. With encryption enabled, each selected client
scales its update by its own integer sample count in plaintext and
encrypts the result with the server's public key
($\mathrm{Enc}(n_k \cdot w_k)$, computed directly rather than via a
second, equally expensive modular exponentiation under encryption); the
server homomorphically sums the selected clients' encrypted,
pre-scaled updates and decrypts only that one aggregate, never an
individual client's contribution. With secure aggregation additionally
enabled, each client's encrypted update is instead routed to one of
$P$ proxy servers (round-robin, $\mathrm{client\_id} \bmod P$), each
proxy blindly sums the encrypted updates it receives and forwards one
partial sum, and the global server blindly sums the proxies' partial
sums before decrypting only the final total -- a collusion-resistance
property beyond direct client-to-server encryption alone, since an
attacker would need to control the server \emph{and} every proxy that
handled a client that round, not the server in isolation.

Encrypting every one of a 45{,}292-parameter model's values
individually with 512-bit Paillier keys does not scale in a naive,
single-process implementation (benchmarked at $\approx$2.3\,ms per
value, $\approx$104\,s to encrypt one client's full update serially).
We parallelize encryption and decryption across all available CPU
cores via a worker pool that receives the public (or private) key once
per pool rather than once per value. Measured on a real training run
(3 rounds, 22 CPU cores, 512-bit keys -- demo-speed only, not
production-secure; 2048-bit keys cost roughly another order of
magnitude of compute): 31--56\,s to encrypt one client's full update,
34--41\,s to decrypt the server's aggregate, per round. Adding the
proxy tier costs almost nothing beyond this: proxy-level aggregation is
plain modular multiplication rather than exponentiation, measured at
0.33--0.41\,s per round regardless of client count.

\section{Experimental Setup}
\label{sec:setup}

\subsection{Synthetic Data}
Data is drawn from a schema-matched synthetic PaySim-style
generator~\cite{lopezrojas2016paysim}, producing overlapping -- not
disjoint -- feature distributions for fraud and legitimate transactions,
with 12\% of fraud transactions deliberately drawn from the
\emph{legitimate} distribution (``quiet fraud'') to avoid a trivially
separable benchmark. Ten clients are generated with independent,
non-identical transaction distributions. All synthetic-data models in
Section~\ref{sec:results} are evaluated on one shared, never-trained-on
held-out test set of 6{,}000 sequences (362 fraud, a 6.03\% fraud rate),
pooled across all clients.

\subsection{Real-World Data}
\label{sec:realdata}
We additionally evaluate on 1.9 million real PaySim
transactions~\cite{lopezrojas2016paysim}, pre-windowed into 2.86 million
ten-step sequences and partitioned across the same ten simulated
clients. Before this data could be used, we found and fixed a genuine
defect in how it had been delivered: \emph{every client's validation and
test split was 100\% fraud}, with zero legitimate sequences present,
verified on the complete files rather than a sample. A split with only
one class present makes precision, ROC-AUC, and a confusion matrix
undefined, so training against the delivered splits directly would have
produced numbers that looked like metrics but measured nothing.

We first attempted the natural-seeming fix of pooling each client's
train, validation, and test rows together and re-splitting with proper
stratification. This was the wrong fix: it merely redistributed the
same corruption evenly, producing a uniform $\approx$30\% fraud rate in
every resulting split for every client, nowhere near real PaySim's
documented $\approx$0.13\% rate -- proof that the delivered
validation/test files were a separate, inflated fraud pool bolted onto
an otherwise clean training file, not simply misassigned legitimate
rows. The working fix discards the delivered validation/test files
entirely and rebuilds all three splits from each client's \emph{training}
file alone (0.04--0.17\% fraud for nine of ten clients, the correct
order of magnitude for real PaySim) via a fresh stratified 70/15/15
split. One client (client 9) is a separate, unexplained anomaly --
46.9\% fraud in its own original training file, roughly three orders of
magnitude above its peers -- carried through unmodified and excluded
from the real-data results below rather than silently normalized, since
its root cause could not be determined (the preprocessing configuration
referenced in the delivered dataset's own metadata does not exist
anywhere in our pipeline).

\emph{Fraud-starvation under real-world imbalance.} Real PaySim's
$\approx$0.1--0.3\% per-client fraud rate, combined with a training
batch size of 64, puts the expected number of fraud examples in a
typical batch below one. Standard loss-level class reweighting
(a positive-class weight in the binary cross-entropy loss) has nothing
to act on in a batch that contains no positive examples at all, and we
verified this empirically: sweeping the positive-class weight from 8 to
400 produced a byte-identical confusion matrix at every setting,
because per-batch gradient-norm clipping saturates the weighting's
effect once the batch itself is starved of signal. Post-hoc decision
threshold tuning on the resulting checkpoint recovered essentially no
additional F1, confirming the bottleneck was upstream of both the loss
function and the operating threshold. We fix this with weighted
oversampling (a per-batch sampler that targets a fixed fraction of
fraud examples per batch, independent of the true class ratio) and
report, in Section~\ref{sec:realdata-results}, that this is necessary
but, for two of the four compared models, not sufficient on its own:
models lacking FedProx's proximal term or DP's noise as additional
training-time regularization remained unable to learn past oversampling
alone.

\subsection{Model Comparison Protocol}
Four models are compared under identical evaluation conditions, on both
the synthetic and real datasets:
\begin{itemize}
\item \textbf{Centralized RandomForest} -- all clients' raw data pooled,
no privacy.
\item \textbf{Centralized Deep} -- the same Temporal Graph Transformer
architecture, all clients' raw data pooled, no federation and no DP.
Isolates the cost of federation alone.
\item \textbf{Federated (FedAvg, no DP)} -- data never pooled, but no
differential privacy applied. Isolates the cost of DP alone.
\item \textbf{Federated (FedProx + DP)} -- our full system.
\end{itemize}

\textit{Reproducibility.} All experiments use a fixed random seed (42)
for data generation and training. Synthetic-data experiments use
$R=10$ federated rounds, 3-of-10 clients sampled per round, 2 local
epochs per client, clip norm 1.0, and $\varepsilon=100$. Real-data
experiments (Section~\ref{sec:realdata-results}) use a reduced round
and sample budget relative to synthetic (stated per table) given the
substantially larger real dataset's wall-clock cost; this is disclosed
per result rather than left implicit. Code and configuration to
reproduce every table in this paper are provided in the accompanying
repository.

\subsection{Synthetic-Data Privacy-Utility Tradeoff}
\label{sec:epsilon}
Table~\ref{tab:epsilon} and Fig.~\ref{fig:epsilon} report a full sweep
across the DP privacy budget $\varepsilon$ (nominal, as configured --
see Section~\ref{sec:accounting}), everything else held fixed, plus the
no-DP ceiling. The curve has the shape a genuine privacy-utility
tradeoff is supposed to have: a hard floor where the mechanism destroys
the model ($\varepsilon \le 5$), a transition region
($\varepsilon \approx 10$--$20$), and a plateau ($\varepsilon \ge 50$)
where additional noise reduction stops mattering. This shape is, in
itself, evidence that the DP mechanism is doing real work rather than
being an inert configuration flag.

\subsection{Real-Data Results}
\label{sec:realdata-results}
All synthetic-data numbers above remain a pipeline-correctness check,
not a real-world performance claim; this subsection is the real-world
one. We repeat the same two measurements on the real PaySim data

\subsection{Encryption and Secure Aggregation}
Section~\ref{sec:he} reported the real, measured computational
overhead of homomorphic encryption and secure aggregation now wired
into training. We note here, for completeness, that these mechanisms
were verified correct independent of model quality: homomorphic
weighted aggregation was confirmed algebraically identical to plaintext
FedAvg aggregation up to floating-point rounding on synthetic test
vectors before being exercised on real model updates, and the
proxy-tiered variant was verified to correctly handle a proxy receiving
zero client updates in a given round (a real occurrence whenever fewer
clients are selected than proxies configured) without error.

\subsection{Multi-Round Differential Privacy Accounting}
\label{sec:accounting}
Every $\varepsilon$ value reported in Sections~\ref{sec:epsilon}
and~\ref{sec:realdata-results} is a \emph{per-round} budget for the
server's one Gaussian noise draw that round
(Section~\ref{sec:dp-mechanism}). We implement multi-round composition
accounting via R\'enyi differential privacy
(RDP)~\cite{mironov2017rdp}, the standard tight method for composing
Gaussian mechanisms: each round's mechanism is converted to its R\'enyi
divergence at a range of orders $\alpha$, RDP composes by simple
addition across rounds at each fixed $\alpha$, and the sum is converted
back to a single $(\varepsilon,\delta)$-DP guarantee by selecting
whichever $\alpha$ gives the tightest result.

Implementing and validating this accountant surfaced a finding more
significant than ``no cumulative total previously existed.'' The
classical Gaussian-mechanism calibration this project uses throughout
(Section~\ref{sec:dp-mechanism}, following Dwork and
Roth~\cite{dwork2014dp}) is proven tight only for $\varepsilon \le 1$.
We verified numerically, across the actual range of nominal
$\varepsilon$ this project uses, that the RDP-tight \emph{true}
single-round privacy cost diverges substantially above that threshold:

\begin{table}[!t]
\caption{Nominal vs.\ RDP-tight true single-round $\varepsilon$ ($\delta=10^{-5}$)}
\label{tab:eps-correction}
\centering
\begin{tabular}{@{}lccc@{}}
\toprule
Nominal $\varepsilon$ & True RDP-tight $\varepsilon$ & Ratio \\
\midrule
0.1   & 0.099   & 0.99 \\
1.0   & 1.01    & 1.01 \\
10.0  & 12.0    & 1.20 \\
50.0  & 102.9   & 2.06 \\
\textbf{100.0 (project default)} & \textbf{313.2} & \textbf{3.13} \\
\bottomrule
\end{tabular}
\end{table}

Within the classical formula's proven regime ($\varepsilon \le 1$) the
nominal and true values agree closely. This project operates at
$\varepsilon = 50$--$2000$ out of practical necessity
(Section~\ref{sec:dp-mechanism}'s $\sigma\sqrt{d}$ scaling against a
45{,}292-parameter model), which is exactly the regime in which the
classical formula understates the true cost. This is not a new defect
introduced by adding composition accounting -- it is a pre-existing
property of every $\varepsilon$ this project has ever reported,
measurable only now because RDP accounting, which carries no such
regime restriction, provides an independent way to check it.

Table~\ref{tab:accounting-real} reports the full cumulative picture
from an actual 15-round real-data training run at nominal
$\varepsilon=100$: naively multiplying the nominal label by the round
count substantially understates the true cost; naively summing the
\emph{true} per-round cost is a valid but loose upper bound; and
RDP composition gives the tight answer in between.

\begin{table}[!t]
\caption{Cumulative $\varepsilon$ after 15 real-data training rounds (nominal per-round $\varepsilon=100$, $\delta=10^{-5}$)}
\label{tab:accounting-real}

\begin{tabular}{@{}lc@{}}

\midrule
Nominal label $\times$ 15 rounds (invalid) & 1{,}500.0 \\

RDP composition is demonstrably doing real work: 3{,}629.9 is
$\approx$23\% tighter than naively summing the true per-round cost
(4{,}697.8). But the honest total is still $\approx$2.4$\times$ what
the commonly quoted nominal ``$\varepsilon=100$'' label alone would
suggest. We report this in full rather than retroactively rounding
earlier sections' nominal labels: this project's actual cumulative
privacy budget over a real training run is in the thousands, not the
hundreds, and closing that gap -- via per-example gradient clipping
(e.g.\ with Opacus, a listed but so far unused dependency in this
project) to reduce the effective dimensionality DP noise must cover, or
a smaller per-round $\varepsilon$ made viable by further right-sizing --
is the clearest concrete next step this accounting identifies
(Section~\ref{sec:conclusion}).

\subsection{Engineering Lessons}
\label{sec:lessons}
We report defects found and fixed during development, beyond the data
and accounting findings already detailed in
Sections~\ref{sec:realdata} and~\ref{sec:accounting}, because each one
would have independently produced a misleadingly clean result if left
uncaught.

\textit{1) A trivially separable synthetic benchmark.} An early version
of the synthetic data generator drew fraud and legitimate transactions
from disjoint value ranges. Every model, including a RandomForest with
no access to sequence structure, achieved 100\% accuracy -- not because
any model was good, but because the benchmark was trivial. We rebuilt
the generator with overlapping distribution families and a 12\%
``quiet fraud'' fraction.

\textit{2) An over-parameterized, collapsing model.} At
hidden\_dim=128 ($\approx1.07$M parameters), the model would collapse
to a constant output (0\% recall, ROC-AUC exactly 0.5) once class
imbalance and DP noise were both present. We right-sized to
hidden\_dim=32 ($\approx45$K parameters), added a prior-informed bias
initialization, and a class weight on the loss -- which also dropped
the usable DP $\varepsilon$ floor by roughly two orders of magnitude,
purely from right-sizing, exactly as $\sigma\sqrt{d}$ scaling predicts.

\textit{3) A NaN-masking bug hiding a real training failure.}
Guarding every loss term with a NaN-to-zero substitution prevented
crashes but let the model silently continue training on a degenerate
prediction once corrupted, because a NaN auxiliary loss term corrupted
the total loss via $0.0 \times \mathrm{NaN} = \mathrm{NaN}$ even at zero
loss weight (IEEE~754 semantics). We fixed this by sanitizing model
outputs at their source, and by adding per-round checkpoint rollback so
a collapsed round cannot poison subsequent training.

\textit{4) A Windows-specific multiprocessing crash in dormant reference
code.} Wiring the homomorphic encryption reference implementation into
live training (Section~\ref{sec:he}) immediately surfaced a
\texttt{UnicodeEncodeError} crash from emoji characters in its
diagnostic output on Windows' default console encoding, and separately
a process-pool crash that only reproduced when invoked through the
actual training entry point rather than an isolated interactive test --
both strong evidence the reference code had never previously been run
end-to-end on this platform, consistent with it having been
disconnected from training until this work.

\section{Conclusion and Future Work}
\label{sec:conclusion}
We presented a federated, differentially private, homomorphically
encrypted fraud detection system and, more importantly, measured
evidence for its central claims -- on both synthetic and real data --
rather than assuming them. Differential privacy has a real, quantifiable
cost on synthetic data (Table~\ref{tab:epsilon}) and does real,
independently confirmed work on real data too
(Table~\ref{tab:epsilon-real}), where it costs close to nothing and in
one regime slightly \emph{helps}, acting as training-time
regularization under severe class imbalance. Homomorphic encryption and
secure aggregation are no longer reference code but genuinely exercised
in training, with real, disclosed computational overhead
(Section~\ref{sec:he}). And implementing formal multi-round privacy
accounting did more than add a missing total: it corrected every
$\varepsilon$ this project has reported, a finding we consider at least
as important as the headline utility numbers, in keeping with this
paper's governing principle that a privacy-utility claim is only as
trustworthy as the accounting and pipeline behind it.

Future work is scoped around four concrete directions, each with a
clear starting point already in place rather than an open question.
First, modeling genuine per-institution non-IID data instead of
independent samples from shared distributions. Second, wiring the
graph branch to real cross-account entity links: the heterogeneous
graph encoder itself is already implemented (Section~\ref{sec:graphbranch})
and only needs entity-linked edge data the current preprocessing does
not yet produce. Third, diagnosing client 9's real-data anomaly
(Section~\ref{sec:realdata}) now that it has been isolated and
documented rather than silently corrected. Fourth, per-example
gradient clipping to bring the corrected cumulative $\varepsilon$ in
Table~\ref{tab:accounting-real} (Section~\ref{sec:accounting}) down
from the thousands toward a range more consistent with the
differential privacy literature's typical operating points, without
reintroducing the parameter-count-driven instability documented in
Section~\ref{sec:lessons}.
